# Compliance Register — ทะเบียนกฎหมาย SHE และการติดตามความสอดคล้อง
> ชื่อโค้ดภายใน (repo/codename): LexGuard · ชื่อทางการ/ผู้ใช้เห็น: **Compliance Register**

ระบบเว็บแอปสำหรับ จป.วิชาชีพ ของ **บริษัท จัสเทล เน็ทเวิร์ค จำกัด** ใช้จัดการทะเบียนกฎหมาย
ความปลอดภัย อาชีวอนามัย และสภาพแวดล้อมในการทำงาน (SHE) รวมถึงกฎหมายอื่นที่เกี่ยวข้อง
พร้อมประเมินความสอดคล้องรายข้อ ติดตามงานที่ต้องทำ สรุปกฎหมายด้วย AI และตารางการสื่อสารองค์กร (ISD-86)

สร้างด้วย **React + Vite + Supabase (PostgreSQL) + Vercel + Claude API**

---

## เมนูหลัก (7 อัน + เมนูย่อย)
1. **Dashboard** — KPI ภาพรวม (จำนวนกฎหมาย/ข้อปฏิบัติ/ยังไม่สอดคล้อง/% ความสอดคล้อง),
   ความสอดคล้องรายหมวด, รายการยังไม่สอดคล้อง (NC), สถิติรายเดือน (พับเก็บได้),
   การ์ดข้อย่อยที่ยังไม่ได้ดำเนินการ แยกตามระดับความเสี่ยง (P24)
2. **ทะเบียนกฎหมาย** — 3 แท็บในหน้าเดียว:
   - *ทะเบียนกฎหมาย* — ค้นหา/กรอง, ดูรายละเอียด, ประเมิน 4 สถานะรายข้อ (บันทึกลงฐานทันที),
     เพิ่มกฎหมาย, ตรวจรายเดือน, ลิงก์ตัวบทต้นฉบับ (📄), ส่งออก Excel / PDF (F-259),
     แผงคัดกรองความเกี่ยวข้องกับกิจการ (เข้าคิว + ประมวลผลคิว)
   - *กฎหมายที่ยกเลิก* — ดู/กู้คืน/แทนที่ + พิมพ์ทะเบียนกฎหมายที่ยกเลิก
   - *ประวัติการทำรายการ* — audit trail แยกตามหมวด
3. **รายการที่ต้องทำ** — รวมงานค้างจาก 3 แหล่ง (ทวนสอบกฎหมาย · รายงานราชการ · การสื่อสาร)
   อ่านจาก view `lg_tasks` แท็บ ต้องทำ / กำลังดำเนินการ / เสร็จแล้ว จัดกลุ่มตามกำหนดเวลา
4. **แผนปรับปรุง** — รายการ NC + เปิด/แก้/ปิดแผนได้ในหน้านี้เลย (อ้าง PD-05)
   แสดงแผนอินไลน์ใต้ข้อ NC พร้อมผู้รับผิดชอบ/กำหนดเสร็จ/เตือนเมื่อเลยกำหนด + พิมพ์เป็นเอกสาร
5. **สื่อสาร & ส่งรายงาน** — ตารางการสื่อสาร (ISD-86) + ส่งรายงานราชการ (เพิ่ม/แก้/บันทึกการส่ง)
6. **สรุปกฎหมาย (AI)** — วางข้อความ/ลิงก์/PDF ให้ AI สรุปเป็นข้อปฏิบัติ พร้อมส่งต่อเข้าทะเบียน
   + ประวัติการสรุป + สั่งสรุปย้อนหลังฉบับที่ยังไม่มีสรุป
7. **เริ่มต้นใช้งาน** (P22) — สายงาน 5 ขั้น + ศัพท์ที่ใช้ในระบบ + ข้อจำกัดที่ควรทราบ

เมนูรอง: **การแจ้งเตือน** (กระดิ่งบน header) · **ตั้งค่า** (ปุ่มเฟืองมุมล่างซ้าย / เมนูผู้ใช้ — เฉพาะ admin)

> **หน้า Gap Analysis ถูกถอดออกจากเว็บแล้ว** (ส.ค. 2569 · commit `5b082f1`) เพราะย้ายไปทำใน Skill
> `src/lib/gap.js` · `src/lib/gapInsight.js` · `src/pages/GapReport.jsx` ถูกลบทั้งไฟล์
> ตรรกะการนับเขียนใหม่ฝั่ง server ที่ `api/_lib/gap-collect.js` แล้วแสดงผล**รายฉบับ**
> ในลิ้นชักกฎหมาย (ขั้นที่ 6) แทนหน้ารวมแบบเดิม

## สายงาน AI 6 ขั้น (ต่อกฎหมาย 1 ฉบับ)

ทุกขั้นเป็น **ข้อเสนอ** เขียนลงตารางที่พักของตัวเอง — ไม่มีขั้นใดเปลี่ยน `lg_requirements.status`
หรือ `lg_law_relevance.confirmed_verdict` ให้อัตโนมัติ ต้องมีคนกดยืนยันเสมอ

| ขั้น | ทำอะไร | endpoint | ปุ่มอยู่ที่ |
|---|---|---|---|
| 0 | อ่านตัวบท แตกเป็นข้อปฏิบัติ + ตามกฎหมายที่อ้างถึง | `law-analyze` + `law-relate` | สรุปกฎหมาย (AI) |
| 1 | คัดกรองความเกี่ยวข้องกับกิจการ | `law-screen` | ทะเบียน (คิว) · ลิ้นชัก |
| 2 | สิ่งที่ต้องทำ / เอกสาร / หลักฐาน | `law-action-guide` | ลิ้นชักรายฉบับ |
| 3 | เสนอสถานะรายข้อ | `req-preassess` | ลิ้นชักรายฉบับ |
| 4 | แตกข้อกำหนดเป็นข้อย่อยที่ประเมินได้ทีละข้อ | `req-breakdown` | ลิ้นชัก (รายข้อ) |
| 5 | สรุปภาพรวมทั้งฉบับข้ามมาตรา | `law-overview` | ลิ้นชักรายฉบับ |
| 6 | สรุปช่องว่างระดับฉบับ | `law-gap` | **ไม่มีปุ่มบนหน้าจอ** |

**ขั้นที่ 6 เป็นลูกผสม กติกา + AI** — `api/_lib/gap-collect.js` คัดข้อย่อยที่ยังไม่ทำและ
นับตัวเลขให้เสร็จก่อน *ไม่เรียก AI เลย* แล้วส่งตัวเลขสำเร็จรูปเข้า prompt โดยสั่งห้ามนับซ้ำ
เพราะโมเดลภาษานับของผิดเป็นปกติ และตัวเลขชุดนี้จะถูกอ้างต่อในการตรวจ ISO 45001
· ไม่มีข้อ unmet → บันทึกผลโดยไม่เรียก AI · ยังติ๊กไม่ครบ → ตอบ 428 ไม่เรียก AI
· รหัสข้อย่อยที่ AI ตอบกลับถูกตรวจทุกตัวว่าอยู่ในชุดที่ส่งไปจริง ตัวที่ไม่อยู่ถูกตัดทิ้ง

**งานหลายฉบับต้องผ่านคิว** (กติกาข้อ 6 · ห้ามวนยิง AI จากหน้าจอ) — `api/queue-run.js`
มีทะเบียนงาน 6 ประเภท (`law_screen` · `law_action_guide` · `law_overview` ·
`req_breakdown` · `req_preassess` · `law_gap`) แต่ละตัวเรียกฟังก์ชันที่ export ไว้ในไฟล์ของขั้นนั้น
คิวใช้ `lg_agent_queue` โดยจับคู่ลงคอลัมน์เดิม (`category_guess`=ประเภทงาน, `source_url`=รหัสอ้างอิง)

> ⚠️ ปัจจุบัน**มีปุ่มบนหน้าจอสั่งคิวได้เฉพาะ `law_screen`** (แผงคัดกรองในหน้าทะเบียน)
> โซน "วิเคราะห์ครบวงจร" ที่เคยสั่งได้ทั้ง 6 ขั้นถูกตัดออกแล้ว (commit `baf50f5`)
> อีก 5 ประเภทยังทำงานได้ปกติ แต่ต้องเรียก endpoint ตรง หรือกดปุ่มรายฉบับในลิ้นชัก

## โมเดลการประเมินความสอดคล้อง (P18 → P21 → P22 → P24)
- **P21**: สถานะมี 4 ค่า `met` (C) / `unmet` (NC) / `acknowledged` (Ack) / `not_applicable` (-)
  Ack และ ไม่เกี่ยวข้อง **บังคับกรอกเหตุผล** (CHECK ใน migration 044)
- **P22**: "ยังไม่มีผู้ประเมินจริง" ใช้ `evaluated_by IS NULL` เป็นตัวชี้ (572/575 แถว)
  ไม่ใช่ `evaluated_at` อีกต่อไป เพราะ migration 044 เติมค่าให้ครบทุกแถวไปแล้ว
- **P22**: AI เสนอสถานะได้ (`lg_req_ai_suggestion`) แต่ต้องมีคนกดรับเสมอ
  เกณฑ์ตัดสิน 4 สถานะอยู่ที่ `ASSESS_CRITERIA` ใน `src/lib/supabase.js` — แหล่งความจริงเดียว
  ที่ทั้ง prompt ฝั่ง server และปุ่ม (i) บนหน้าจอใช้ร่วมกัน
- **P24 · ประเมินระดับข้อย่อย** — ระบบเดิมละเอียดสุดที่ระดับ "ข้อกำหนด" จึงตอบได้แค่สอดคล้อง/ไม่
  แต่ตอบไม่ได้ว่าไม่สอดคล้องตรงจุดใด (ตรวจวัดเสียงแล้วแต่เก็บผลไม่ครบปีที่กำหนด = ช่องว่างอยู่ที่
  ระยะเวลาเก็บ ไม่ใช่การตรวจวัด) · `lg_sub_requirements` แตกเป็นข้อย่อยที่ติ๊กได้ทีละข้อ
  3 ปุ่ม (ทำแล้ว / ยังไม่ทำ / ไม่เกี่ยวข้อง) + หลักฐาน + ความเสี่ยง 4 ระดับ
  view `lg_sub_req_progress` คำนวณ `suggested_status` เป็น**ข้อเสนอ** ต้องกดยืนยันก่อนเสมอ
- ประเมินรายข้อ **inline ในหน้าเพิ่มกฎหมาย**: สอดคล้อง / ไม่สอดคล้อง / รอผู้เกี่ยวข้องประเมิน
- **% ความสอดคล้อง = met / (met + unmet ที่ประเมินแล้ว)** — ข้อที่ "รอประเมิน" ไม่รวมทั้งเศษและส่วน

## ข้อมูล (ยึดฐานข้อมูลสดเป็นหลัก)
- **7 หมวด**: LA–LG (CCS/CC ถูกถอดออกแล้ว)
- **160 ฉบับ** (บังคับใช้ 150 + ยกเลิก 10) · **575 ข้อปฏิบัติ**
  (met 539 · unmet 13 · acknowledged 23 · not_applicable 0 · ไม่มีผู้ประเมินจริง 572)
- รายงานราชการ ~19 รายการ · การสื่อสาร ~26 รายการ · แผนก (`lg_departments`) 16 แผนก
- ตารางทั้งหมดใช้ prefix `lg_`

> ⚠️ **ฟีเจอร์ AI ขั้น 1-6 ยังไม่เคยถูกใช้จริงสักฉบับ** (ตรวจฐานสดเมื่อ 29 ส.ค. 2569) —
> `lg_law_relevance` · `lg_law_action_guide` · `lg_sub_requirements` · `lg_req_ai_suggestion` ·
> `lg_law_gap` = 0 แถวทั้งหมด และ `lg_company_profile` ก็ยังว่าง ซึ่งทำให้ขั้นคัดกรอง (1) เริ่มไม่ได้
> **ต้องตั้งโปรไฟล์บริบทองค์กรที่หน้าตั้งค่าก่อน** สายงาน AI ถึงจะเดินได้

> ⚠️ ตัวเลขด้านบนเป็นค่า ณ เวลาเขียน — ให้ยึดหน้า Dashboard ในแอป หรือ `SELECT count(*) …`
> จากฐานข้อมูลสดเสมอ

## ตารางฐานข้อมูลหลัก (prefix `lg_`)

**ทะเบียนและการประเมิน**
- `lg_laws` · `lg_requirements` · `lg_categories` — ทะเบียนกฎหมาย + ข้อปฏิบัติ + หมวด
- `lg_sub_requirements` (mig 054) — ข้อย่อยที่ประเมินได้ทีละข้อ **รวมนิยามกับผลติ๊กไว้ตารางเดียว**
- `lg_sub_req_progress` (**view**, mig 054) — ความคืบหน้าต่อข้อกำหนด + `suggested_status`
- `lg_improvement_plans` — แผนปรับปรุงรายข้อ (CAR/OFI อ้าง PD-05)
- `lg_law_workflow` — งานทวนสอบ/ประเมินรายกฎหมาย (2 workflow: add / monitor)

**ที่พักของข้อเสนอจาก AI** (ไม่มีตัวใดเขียนทับทะเบียนจริง)
- `lg_law_relevance` (mig 047) — ผลคัดกรองความเกี่ยวข้อง + `confirmed_verdict` ที่คนกดยืนยัน
- `lg_law_action_guide` (mig 048) — สิ่งที่ต้องทำ / เอกสาร / หลักฐาน
- `lg_req_ai_suggestion` (mig 049) — สถานะที่ AI เสนอรายข้อ
- `lg_law_gap` (mig 055) — สรุปช่องว่างระดับฉบับ · `gaps` จาก AI · `stats` จากกติกาคำนวณ
- `lg_agent_queue` · `lg_agent_runs` — คิวงานเป็นชุด (จับคู่ลงคอลัมน์เดิมของ mig 006)

**อ้างอิงและบันทึก**
- `lg_req_f259_source` (mig 052) + `lg_req_effective` (**view**) — ค่าที่กู้จาก F-259
- `lg_law_refs` · `lg_ref_answers` (mig 040/041) — ตัวบทที่ถูกอ้างถึง + cache ตาม `topic_key`
- `lg_reports` · `lg_communications` — รายงานราชการ + ตารางการสื่อสาร
- `lg_tasks` (**view**, mig 030) — รวมงานที่ต้องทำจาก workflow/report/comm, `security_invoker`
- `lg_company_profile` (mig 047) — บริบทองค์กร (ขั้นคัดกรองต้องใช้)
- `lg_departments` · `lg_review_log` · `lg_activity_log` · `lg_notification_log` ·
  `lg_ai_discovered_laws` · `lg_settings` · `lg_attachments`

## ข้อจำกัดที่รู้ตัว (ต้องระบุในเอกสารส่งมอบ)
1. **ไม่มีประวัติการประเมินหลายรอบ** — migration 054 รวมนิยามข้อย่อยกับผลติ๊กไว้ตารางเดียว
   จึงเก็บผลได้ชุดเดียวต่อข้อย่อย · การตรวจ ISO 45001 มักขอดูผลรอบก่อนเพื่อดูแนวโน้ม
   เหตุผลที่ตัดสินใจแบบนี้เขียนไว้ในหัวไฟล์ `054_sub_requirements.sql` — ระบบไม่มีตารางการประเมินจริง
   (`lg_law_workflow` / `lg_assessment_flow` ว่างทั้งคู่ ผลประเมินจริงอยู่ที่ `lg_requirements`)
2. **ข้อย่อยที่ AI สร้างควรให้ผู้มีความรู้ด้านกฎหมายตรวจทานก่อนเปิดใช้จริงอย่างน้อยหนึ่งรอบ**
   เพราะถ้าแตกข้อย่อยผิดตั้งแต่ต้น ผลประเมินทั้งหมดที่ตามมาจะผิดตามไปด้วย
3. `lg_sub_requirements.context_level` บอกว่าข้อย่อยชุดนั้นแตกจากบริบทครบแค่ไหน
   (`full` / `partial` / `bare` / `unknown` = แถวที่มีก่อน mig 055 ซึ่งรู้ย้อนหลังไม่ได้)
   หน้าจอขึ้นป้ายเตือนเมื่อไม่ใช่ `full` — ควรทำขั้น 2 และ 5 ให้เสร็จก่อนแล้วกด "แตกใหม่"
4. ระบบบันทึกเสมอว่าข้อมูลใดมาจาก AI และข้อมูลใดผ่านการยืนยันจากผู้ประเมิน
   การตัดสินสถานะความสอดคล้องขั้นสุดท้ายเป็นดุลพินิจของผู้ประเมินที่มีคุณสมบัติ

## Environment Variables (ตั้งใน Vercel)
- `VITE_SUPABASE_URL` — URL ของโครงการ Supabase
- `VITE_SUPABASE_ANON_KEY` — publishable key (ฝังใน client ได้)
- `VITE_AUTH_MODE` — `demo` (ทดลอง) หรือ `supabase` (ใช้จริง)
- `VITE_DEMO_PASSWORD` — รหัสผ่านบัญชี demo (ถ้าไม่ตั้ง จะล็อกอินโหมด demo ไม่ได้)
- `ANTHROPIC_API_KEY` — คีย์ Claude สำหรับทุก endpoint ใน `api/` (server-side เท่านั้น)
- `ANTHROPIC_MODEL` — ทับโมเดลที่ใช้ (ไม่ตั้ง = `claude-sonnet-4-6`)
- `ALLOWED_ORIGIN` — โดเมนของแอปเอง ใช้ตรวจ Origin/Referer ของทุก endpoint ผ่าน `api/_lib/guard.js`
  (รองรับหลายค่า คั่นด้วย comma)

> หมายเหตุ: flow "เฝ้าระวังกฎหมายอัตโนมัติ" (Vercel Cron + `api/agent-*`, `api/law-update`)
> ถูกถอดออกแล้ว — ไม่ต้องตั้ง `CRON_SECRET` อีก

## ⚠️ หมายเหตุด้านความปลอดภัย (ทำก่อนขึ้นใช้จริง / ก่อนเปิด repo สาธารณะ)
1. **ลบบัญชีที่ฝังรหัสในโค้ด** ใน `src/lib/auth.js` (`APP_ACCOUNTS`) — มี username/password hardcode
   ถ้ารีโปเป็น public = ใครก็ล็อกอินเป็น admin ได้ · ให้ย้ายไป Supabase Auth และเปลี่ยนรหัสทันที
2. **RLS**: สิทธิ์ในหน้าเว็บเป็นเพียง UI · ให้เพิ่ม policy จำกัดสิทธิ์ที่ฐานข้อมูลก่อนใช้งานวงกว้าง
3. ปิด `VITE_SKIP_LOGIN` ใน production (ให้สิทธิ์ guest = admin)
4. พิจารณาตั้งรีโปเป็น **private** (ถ้าเคย push รหัสไปแล้ว ให้ล้างประวัติ git ด้วย)
